# Module 06 — AI layer (providers, prompts, generation, logs)

Status: complete (Phase 6)

## 1. Purpose and place in the process

Gives AutoBlogix an AI writing layer: an interface + pluggable providers
(development stub by default, real OpenAI-compatible API when a key is
added), seeded prompt templates, a composer page that turns a title into a
ready-to-edit draft, a per-post generate/regenerate action, and per-post AI
history. Generation output lands in exactly the columns Phase 5 already
sends to WordPress (`content`, `excerpt`, `tags`, `keywords`,
`meta_description`).

Phase boundaries:

- **Phase 4** owns manual CRUD and the draft ↔ scheduled save rule; AI
  statuses (`generating`/`generated`) are this phase's and survive edits.
- **Phase 5** owns publishing; this phase must not clobber publish states
  and simply makes generated posts publishable through the same entry
  (see rule 9).
- **Phase 7** picks up `scheduled` posts — generated posts reach that state
  by editing in a schedule (rule 9).

`generating → generated` on success; `source = ai` for composer-created

`content`, `excerpt`, `tags`, `keywords`, `meta_description`.

## 5. Business rules / edge cases

1. **Status gate:** generation runs for `draft`, `generated`, and
   `generating` (a *visible* `generating` state means the previous
   synchronous attempt died — re-entry is the recovery path; interrupted
   `processing` log rows are closed as failed first). All other statuses →
   result `not_allowed`, nothing written, no provider call.
2. **Idempotent-ish entry:** status check + flip to `generating` happen in
   one `lockForUpdate` transaction (same shape as Phase 5); the provider
   call runs outside any transaction; success → `generated`, failure →
   previous status restored.
3. **Provider resolution** (`AiProviderManager::forUser`): the user's
   **active** `ai_providers` row wins; otherwise the environment
   (`config('ai.provider')`) — `development` → `DevelopmentAiProvider`,
   `openai` + key → `OpenAiProvider`, unknown/missing key → development
   (safe default, logged). API keys are read through the encrypted cast
   and never logged or re-displayed (masked last-4 hint only).
4. **Prompt resolution:** `prompt_templates` row by key
   `blog_post_generation` → else `config('ai.defaults.…')`; the seeder
   copies config into the table (`updateOrCreate`, idempotent). Placeholders
   `:title :topic :keywords :tone :length_words` substituted with `strtr`.
5. **Defensive parsing** (`AiResponseParser`): strip markdown fences and
   surrounding prose, extract the outermost `{…}`, `json_decode`; on any
   failure throw `AiProviderException` with a friendly message. Output is
   normalized: `content` must be non-empty (else friendly error), `excerpt`
   derived from stripped HTML when missing, `tags`/`keywords` coerced to
   clean string arrays (≤ 5 / ≤ 10 entries, ≤ 50 chars, de-duplicated),
   `meta_description` ≤ 300 chars or null, optional `tokens_used` passthrough.
6. **AI HTML is sanitized at ingest** with `HtmlSanitizer` (the same
   allowlist the preview uses), so generated content is safe in the UI
   *and* on the way to WordPress.
7. **Failures are data:** provider errors (`AiProviderException`) and
   unexpected throwables both → friendly flash, `ai_logs` row closed
   `failed` with the technical detail, `Log::warning`/`error` with technical
   detail, post restored — never a 500, never a stuck `generating` status.
8. **Providers UI:** store = add config (new one becomes the single active
   row, others deactivated in the same transaction); activate flips the
   active row; delete returns to the environment fallback. `base_url`
   validated with `UrlNormalizer::isAllowedUrl` (SSRF rules shared with
   websites — no 192.168.* / metadata IPs, http allowed in local env).
9. **AI → publishing bridge:** `generated` posts get the same affordances
   as drafts: show page offers **Publish now** (entry transitions
   `generated → scheduled → publishing` inside the lock, keeping the
   "only scheduled/failed publish" rule), and editing in a schedule date
   moves `generated → scheduled` so Phase 7's scheduler can pick it up.
10. Flagged improvements (post-MVP): queued generation for long provider
    calls; a prompt editor (belongs with Settings in Phase 8); token/cost
    dashboards; per-user prompt templates.

## 6. UI pages and states

- **`/ai-content` (AI Content composer):** website select, title,
  topic (optional), keywords (comma-separated), tone select
  (friendly/professional/casual/authoritative), length select
  (short ≈400 / medium ≈800 / long ≈1500 words). No websites → "Add a
  website first" CTA (posts pattern); validation errors redisplay with
  `old()`. Success → new draft post, `source=ai`, status `generated`,
  redirected to its show page with a success flash; generation failure →
  the draft still exists (manual writing possible) with an error flash.
- **posts.show:** `draft` (empty content) → **Generate content**;
  `draft`/`generated` with content → **Regenerate** (confirm modal — it
  replaces fields); `generating` → disabled **Generating…**; other
  statuses → no button. New **AI history** table: time, provider/model,
  status badge, tokens, error detail. Generated posts also show the
  publish action (rule 9).
- **`/ai-providers` (AI Providers):** active provider state (or "using the
  built-in development provider" when falling back to the environment),
  table of configs (provider, model, masked key, active badge) with
  activate/delete, and an add form (provider select, API key write-only,
  model, optional base URL). Keys never re-rendered.

## 9. As built

Implemented exactly as specified above, with these final details:

- **Routes**: `ai.generate` (GET composer) · `ai.store` (POST composer) ·
  `posts.generate` (POST per-post action) · `ai.providers` +
  `ai.providers.store|activate|destroy`. All under `auth` + `verified`;
  nav Phase 1 links resolve now.
- **Services (flat in `app/Services/`)**: `AiProviderInterface`,
  `DevelopmentAiProvider` (deterministic — same input, same post), `OpenAiProvider`
  (bearer auth, one HTTP attempt, status → friendly-message map, fenced/prose
  JSON via `AiResponseParser`), `AiProviderManager` (active DB row →
  env `config('ai.provider')` → development fallback + `Log::warning`),
  `AiContentService` (transactional status entry, log lifecycle, output
  validation, `HtmlSanitizer` at ingest, restore-on-failure).
- **AI failures never 500**: `AiProviderException(friendly, technical)` —
  friendly string is the flash, technical string goes to `ai_logs.error_message`
  + `Log::warning`/`error`. Unexpected throwables are caught the same way.
- **`generating` re-entry = crash recovery** (generation is synchronous; a
  visible `generating` state means the previous attempt died). Interrupted
  `processing` rows are closed as failed before the new attempt opens.
  Result codes: `generated | not_allowed | provider_failed`.
- **Phase 1 columns reused**: `blog_posts.ai_provider` / `ai_model` are set on
  success (show-page sidebar had them since Phase 1).
- **Bridge changes to earlier phases**: `BlogPostService::create()` gained
  `PostSource $source = PostSource::Manual`; `update()` now flips
  `generated + schedule → scheduled`; `PublishingService::requestPublish()`
  treats `generated` like `draft` (→ `scheduled` → `publishing`); show page
  publish button + edit-form schedule field include `generated`.
- **Prompts are global rows** (`prompt_templates`, no `user_id`): seeded
  idempotently from `config('ai.defaults.blog_post_generation')`, DB row wins,
  config is the fallback so generation works before the seeder ran. The
  Phase-1 TODO `User::promptTemplates()` was dropped as a result (no
  per-user prompt editor in MVP — flagged for Phase 8 Settings); `User::aiProviders()`
  and `User::aiLogs()` were added. There is no `AiProvider` policy: the
  owner-scoped `Route::bind('provider')` is the only access path (row is
  always resolved through the session user's relation).
- **Providers UI shows one provider type** (`openai` — OpenAI-compatible,
  incl. OpenRouter via base URL); the manager still honors a `development`
  row value for flexibility. New saves auto-activate (single active row,
  transactional swap).
- **Verification**: `AiTest` **18 tests / 148 assertions**, `AiResponseParserTest`
  **7 / 24**, full suite **167 tests / 765 assertions OK**, Pint clean
  (1 import-order fix), `npm run build` ok, live HTTP smoke **28/28**
  (composer → Generated → regenerate → 2 log rows → provider store/encrypt/
  mask/delete → fallback; DB restored to seeded 0,0,0,0).
